Git client

RequestTailor includes a Git client. It works on any repository, not only on collections, and it talks only to your own Git host.

Collections are plain files, so Git is how you version, review and share them. The app reads and writes the repository itself (gitoxide on the desktop, isomorphic-git in the browser, through the companion rt agent for network access) and does not need the git program. Files of a collection get a field-by-field diff and merge; every other file gets a line diff and a line merge.

History graph

The graph shows branches as lanes, with tags, remotes and signed commits marked. Opening the history of a repository with 100 000 commits shows the first rows in under 1500 ms, and a repository with 10 000 commits scrolls at a 95th percentile frame time of 20 ms (budgets). Select a commit to see its changed files and the semantic diff.

Changes and commits

There is no staging area by default. The commit form lists the changed files with a checkbox each; commit(message, paths) commits exactly those. Before every commit a scanner checks the files for credentials and refuses the commit if it finds one (see secret scanner). The change view shows text diffs with word-level highlights and image diffs, and filters by Staged.

Wizards that explain first

Branch, switch, merge, pull, push, publish, fetch, stash (shown as Park changes), cherry-pick, revert, reset, discard, amend, tags and remotes each open a plan before anything happens. The plan says in plain language which branches move and which files change, and why an action is blocked, for example because of unsaved changes, an unfinished merge, a detached head, no upstream or diverged branches.

  • Backup before every change. Before an action moves a branch or changes working files, the app writes a backup ref refs/requesttailor/backup/<unix time>/<name> and a line in a local action journal.
  • Undo. The last action can be undone. Undo is refused once the refs have moved since, so it never overwrites newer work.
  • No force-push, no rewriting published history. A diverged branch offers a merge or take theirs (a reset, with a backup). Rewriting commits that were already published is blocked.
  • Lost work. The reflog view finds commits that no branch points to any more and restores a branch from them.

Semantic diff and merge

A collection change is shown per field: URL, method, header, parameter, body, auth, script, assertion, setting. Two branches that change different fields of the same request merge without a conflict; only the same field changed differently on both sides is one, and the app asks per field. Secret values never appear in a diff.

The same engine is available outside the app:

rt diff main..feature --json
git config merge.requesttailor.driver "rt merge-driver %O %A %B %P"
echo "*.yml merge=requesttailor" >> .gitattributes

With the merge driver set up, git merge, pull, rebase and cherry-pick merge collection files field by field. Details: Git for APIs in the CLI guide. Comparing 1000 requests with 100 changed takes under 200 ms.

Blame, file history and search

Blame shows per field which commit last changed it. The file history follows renames, and you can restore an old version of a request from it. History search finds commits by message, author, path or content.

Compare two versions by running them

Pick two revisions, for example main and a branch. The compare view lists changed, new, removed and breaking requests, shows both definitions side by side, and can run the changed requests against both versions and show the two responses next to each other: status, headers, timing and a JSON diff. Environments and secrets come from your current setup. rt bisect --good v1.4.0 --bad HEAD finds the first commit at which a request, test or assertion fails; 50 commits take at most 7 runs.

Pull requests

For GitHub and GitLab (also self-hosted), the app lists pull and merge requests, shows their semantic diff and the CI status, runs the changed requests, notes breaking changes against the OpenAPI spec, lets you comment on a line, and creates a pull request or draft. The access token is kept in the OS keychain (desktop) or encrypted in the browser. Calls go only to your host.

Rescue a committed secret

If a credential reached the history, the rescue assistant finds it in HEAD and all local branches, rewrites the local commits after writing a backup, and shows the git push --force-with-lease command and the reminder to rotate the credential. It never pushes by itself. Secret values do not reach the interface; Rust reads them from the repository only to replace them.
