OData and SAP guide

How to work with OData V2 and V4 services from S/4HANA, CAP and RAP. For an overview of the plugin, see SAP and OData.

1. Switch on the OData plugin

Choose SAP and OData at first start, or switch the OData plugin on later in the plugin settings. It asks for three permissions: network access to the host of the request being sent only, its own storage (for cached metadata, CSRF tokens and ETags), and the non-secret variables (for sapClient and sapLanguage).

2. Try it locally

The repository has a synthetic OData test server and three example collections:

cargo run -p rt-odata-testserver          # http://127.0.0.1:47830

Open examples/s4hana-sales, examples/cap-bookshop or examples/rap-salesorder, pick the environment Local, and for the S/4 examples enter the test password RT_PASS as the value of the secret variable password. Each example's README walks through its requests.

3. Connect your own system

  1. Create a collection, or import the service's $metadata (from the system, or an API specification downloaded from the SAP Business Accelerator Hub). The importer creates a request per entity set and operation.
  2. In the plugin's SAP systems tab, create DEV, QAS and PRD environments: host, client, language and user. The password is created as a secret without a value; enter it once and it stays in your keychain.
  3. Pick an environment and send. The plugin adds sap-client and sap-language to the URL unless it already has them.

4. Browse and query

The OData tab of the collection shows the service model from $metadata: entity sets, keys, properties, navigation and operations. On a request, the Query tab builds $filter, $expand, $select, $orderby, $top, $skip and $count or $inlinecount from that model and writes them into the URL.

5. Write: CSRF and ETags

SAP Gateway and many CAP deployments protect writes with a CSRF token bound to the session cookie. Before a modifying request without X-CSRF-Token, the plugin fetches one with X-CSRF-Token: Fetch in the same session as the request and sets it. When the server answers 403 with X-CSRF-Token: Required, the next send fetches a new token.

For optimistic locking, read the entity first. The plugin remembers its ETag and sets If-Match on the next update or delete of that entity, unless you set the header yourself. In OData V2 the update method is usually MERGE (newer Gateway releases accept PATCH); in V4 it is PATCH.

6. $batch

The Batch tab composes a $batch request from read parts and changesets (all-or-nothing groups of writes), as multipart for V2 and V4 or as JSON for V4, and shows each part of the response with its status. A batch is an ordinary request file, so you can also write the body by hand, as the examples do.

7. Drafts in RAP and CAP

Draft-enabled entities have two instances per key, the active one (IsActiveEntity=true) and the draft (IsActiveEntity=false). The Draft tab runs the lifecycle:

8. In a pipeline

The plugin runs in rt send too, with the same CSRF and ETag handling:

rt send sales/read-sales-order.yml --env QAS --var password="$QAS_PASSWORD" \
  --plugin odata.wasm --pretty
