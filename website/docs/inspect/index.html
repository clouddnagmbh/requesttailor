Check and inspect responses

What the app and rt tell you about an answer you already got. None of these send an extra request on their own, and nothing is sent unless you send it.

Timing and trace

The status line of every response has a one-line timing bar; the Timing tab has the full waterfall. Plugins and servers can add segments, such as the server's own time, shown as as reported by <source> and never counted in the total. rt send --timing prints the same bar on stderr.

A trace id helps to find a request in the logs of a server. It is off by default. Set extensions.requesttailor.trace.inject: true in opencollection.yml and requests get a W3C traceparent header unless they already have one; the id shows as a chip with a copy button, and rt send --trace prints it on stderr. Adding it costs at most 0.02 ms.

Response checks

rt send --checks prints one line per observation on stderr and adds them to the report; in the app they show as a chip and a tab. Nine rules look at headers, cookies and the first 1 MiB of the body: missing HSTS, missing nosniff, missing content security policy, missing frame protection, cookie flags, CORS with credentials, a JWT with alg: none, stack traces in error pages and version disclosure. An observation is a hint, not a verdict: it names a header or cookie, one sentence why and one how to fix. All rules over one response cost at most 2 ms; the 1 MiB checks at most 20 ms.

Passive security hints

More rules look at the same responses and tag each finding with a category of the OWASP API Security Top 10 (2023):

  • CORS that reflects any origin;
  • JWTs with a weak HMAC secret (a hint, the secret is never printed), without exp, or used after they expired;
  • tokens in responses that may be cached;
  • no sign of rate limiting;
  • revealing error pages and version numbers;
  • TLS: an old protocol, an expired or soon-expiring certificate, a weak key (native app and rt only; the browser does not tell).

They run on responses you sent anyway, so there is no extra request. A finding never contains a token value. Every rule can be switched off per device or per collection (extensions.requesttailor.security).

JWT reader

Choose a token in a header or a response and the app decodes it: header, claims, and the issue, not-before and expiry times with a countdown. It says signature not verified because it does not check signatures. The token is shown but never written to a file, the history or a report; only claim names and deadlines appear there.

Rate limits

RequestTailor reads Retry-After and the RateLimit headers and shows what is left. With --respect-limits, rt send and rt run wait for the announced time; --max-wait bounds one wait (default 60 s, at most 600 s) and the run ends with the reason if the wait would be longer. The wait is accurate to 50 ms. Off by default.

rt run . --env Staging --respect-limits --max-wait 30s

Pagination

rt send --all-pages follows the pages of a reading request and merges them into one response. The rule comes from the request (<request>.paging.json), the collection or a plugin, and yours always wins; the OData plugin brings rules for @odata.nextLink and d.__next. Limits always apply: 20 pages by default (--max-pages, at most 1000). Following 100 pages of 100 items and merging them takes at most 2500 ms.

Saved views

A view is a named JSONPath expression saved with a request in <request>.views.json. The Views tab shows what it picks from the response, and the CLI prints it:

rt send users/list.yml --view names
rt send users/list.yml --view-expr '$.items[*].id'

Applying a view to a 10 MiB JSON response takes at most 300 ms.

Webhook inbox

rt inbox listens on 127.0.0.1 (default port 47855) and prints every request it gets, answering with a fixed reply (--status, default 200). It keeps requests in memory only and has no tunnel: to receive calls from the internet, point your own tool at the port. The app shows the same inbox. A request reaches the screen within 5 ms of its last byte (median).

Breaking changes in GraphQL and Protobuf

rt changelog and the diff views compare a GraphQL schema (SDL) and Protobuf files between two revisions and list breaking changes first, with the requests that select a changed field or call a changed method. Two versions of a schema with 2000 types take at most 300 ms.
