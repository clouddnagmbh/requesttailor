MCP

MCP (Model Context Protocol) is how AI assistants call tools on servers. RequestTailor works in both directions:

  • Test MCP servers. In the app, RequestTailor is the client: connect to a server, see its tools, resources and prompts, call a tool and keep the call as a test, like an API test.
  • Serve your collection. rt mcp makes your collections available to AI agents, with read and write rules per environment, approvals and an audit log.

Test MCP servers in the app

Open the view MCP in the sidebar. The first visit explains the view and offers Try the demo server; a short checklist walks you through your first test and can be hidden.

  1. Connect to a server by the command that starts it (stdio, desktop only) or by URL (Streamable HTTP). Headers, arguments and environment variables take {{variables}} from the active environment, so tokens stay secrets.
  2. Browse its tools, resources and prompts in tabs.
  3. Call a tool with a form built from its input schema, or as raw JSON. The result shows structured output, text and images, whether the tool reported an error, and the progress and log notifications the server sent before it.
  4. Save as test writes a *.mcp.yaml file next to your collection, with checks on the result. It is a plain file in your repository, like your requests.
  5. Run all runs every saved test of the collection and shows what passed and what failed, and why.

In CI, rt mcp-test runs the same tests and exits with 4 when one fails:

rt mcp-test path/to/collection --env CI

The demo server

A small MCP server with fake data, so you can try all of this without a server of your own. It works offline, gives the same answers every time and needs no account.

WhatShows
echo, addThe simplest call; structured output with an output schema.
fake_weatherA form with a required and a choice argument. The same city always gets the same weather.
todo_add, todo_list, todo_doneState kept per connection.
uuid, image, failStable generated values, image content, a tool error.
countdownProgress and log notifications before the result.
Resources and promptsdemo://readme, demo://cities.json, demo://todos; the prompts summarize and weather_report.
  • In the app, desktop and web, Try the demo server connects to the built-in address rt-demo://mcp. The server runs inside RequestTailor; nothing is installed or started and nothing goes over the network. Tests saved against it also run with rt mcp-test.
  • On a local port (desktop): start the same server on http://127.0.0.1 with a free port to try other MCP clients. It stops when you stop it or quit the app.
  • From the command line: rt mcp-demo speaks MCP on stdin and stdout; rt mcp-demo --http serves http://127.0.0.1:47850/mcp until you stop it.
{
  "mcpServers": {
    "requesttailor-demo": { "command": "rt", "args": ["mcp-demo"] }
  }
}

Serve your collection: rt mcp

rt mcp offers a collection to coding agents as tools over stdin and stdout. It is part of the rt command line and uses the same core as the apps, so an agent sends requests exactly as you would, from the same collection files. In the desktop app, Connect to RequestTailor itself starts it on the open collection, so you see your requests the way an agent does.

Connect an agent

claude mcp add requesttailor -- rt mcp /path/to/collection

Other clients (Cursor, VS Code, Claude Desktop) take the same command in their JSON configuration:

{
  "mcpServers": {
    "requesttailor": {
      "command": "rt",
      "args": ["mcp", "/path/to/collection", "--env-default", "DEV"]
    }
  }
}

Tools

ToolWhat it does
list_requestsPath, name, method and effect (read or write) of every request.
get_requestOne request as in its file; credentials are masked.
list_environmentsThe environments the agent may use, with access and production flag. Secret variables appear by name only.
send_requestSends one request and returns the report with secrets masked.
run_folderRuns a folder or the whole collection like rt run. Every request is checked on its own.

GET, HEAD, OPTIONS and TRACE read; every other method writes. A GraphQL request reads unless its document contains a mutation. gRPC writes, and a WebSocket request writes as soon as it sends messages.

Rules for agents

  • Access per environment. In the app, "Agent access" sets none, read or write for each environment; the rule is stored in opencollection.yml. The default is read only.
  • Approval for production. A request that writes to an environment marked as production waits for you. Approve or deny it in the app banner, with rt approvals, rt approve <id> and rt deny <id>, or in your client if it asks. No answer within five minutes counts as a denial, and nothing is sent.
  • No secret values. Agents work with variable names. Values come from the OS keychain (as for rt send and rt run), from secret managers or from --var, and are masked in everything the agent gets back, also when a server echoes them.
  • Audit log. Every tool call is written to a local log (agents/audit.jsonl in the data folder). Nothing leaves your machine.
  • Fixed policy. rt mcp reads the access rules once at start, so an agent that edits files cannot give itself more access.

The full reference, with all options and the security model, is crates/rt-cli/README.md.
